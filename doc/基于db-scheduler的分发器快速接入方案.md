# 基于 db-scheduler 的分发器：coucou-server 快速接入方案

---

## 1. 设计原因

接入步骤之前，先说清楚为什么这么设计。这一章回答五个问题：要解决什么问题、为什么选 db-scheduler、为什么业务表与调度表分离、为什么用一次性实例、为什么它撑得住用户级的量。

### 1.1 要解决的问题

粉丝日程提醒、角色朋友圈自动发布这类任务有三个共同特征：

- **数量随用户数增长。** 每个用户、每个角色各有一份时间，不是运维手里固定的几十个 cron。
- **频繁修改和取消。** 用户在聊天里说"改到九点""取消提醒"，创作者在 Studio 里单条取消计划。
- **每条有自己的时区和周期。** "每周日 20:00 洛杉矶"和"每天 08:00 上海"混在一起。

这类任务不能一条对应一个 xxl-job 任务。xxl-job 的任务表是为运维级任务设计的，每次触发一条 HTTP 调用加一条日志，控制台列表会被用户数据淹没，用户每改一次时间都要反向调 OpenAPI。调度中心会变成业务库的副本，两边一致性成为新问题。

所以需要一个"分发器"：业务表是真相源，某个机制负责在到点时把该处理的记录交出来。本文选择 db-scheduler 作为这个机制。

### 1.2 为什么选 db-scheduler

分发器有三种实现方式，对 coucou-server 的适配如下：

| 实现 | 到点索引在哪 | 谁负责轮询 | 精度 | 要自己写的部分 |
|---|---|---|---|---|
| xxl-job 每分钟触发加扫业务表 | 业务表自己 | xxl-job | 分钟 | 认领、崩溃恢复、重试退避，约两三百行 |
| **db-scheduler 内嵌**（本文） | scheduled_tasks，与业务表同库 | db-scheduler 自己的线程 | 秒 | 只写 Handler 和三个写入点 |
| Redis ZSET 加 Redisson | Redis | 自写轮询器 | 秒 | 消费即丢失的兜底、重试、对账、周期重算，加一个新中间件 |

选 db-scheduler 的理由：

- **它把分发器里最容易写错的部分做掉了。** 多副本认领用 `FOR UPDATE SKIP LOCKED`，节点崩溃靠心跳回收，失败重试有指数退避，改期取消是现成的 `reschedule` 与 `cancel`。这些自研都要写，而且都是出了问题才发现写错的那种代码。
- **它和 coucou-server 的技术栈完全一致。** Java 加 PostgreSQL 加 Spring Boot，starter 直接从 Maven Central 拉取，编译目标 Java 17，不引入任何新中间件。
- **它的表和业务表在同一个数据库里。** 这一点决定了后面 1.4 节的事务一致性，Redis 路线做不到。
- **秒级精度。** 轮询间隔可以配到 1 秒，xxl-job 扫表路线是分钟级。

不选 Redis 的理由：Redisson 的延时队列只解决"到点后出现在队列里"这一件事，消费后进程崩溃这条就丢了，没有周期、没有重试、取消对已转入队列的那段窗口无效，业务仍要写对账。代码量与自研扫表相当，却多了一个 coucou-server 目前没有的中间件和一套双写一致性问题。

### 1.3 为什么业务表与调度表分离

技术上可以把提醒的全部字段序列化进 scheduled_tasks 的 task_data，不建业务表。但产品要回答的问题远不止"下一次什么时候叫"：

| 产品需要 | 只靠 scheduled_tasks 做不到的原因 |
|---|---|
| 按用户列出全部提醒 | task_data 是二进制，不能按 user_id 查，不能建索引，不能 join |
| 暂停后还能再打开 | cancel 就是 DELETE，暂停后这条在表里不存在 |
| 仅一次的提醒执行完显示"已送达" | 一次性任务执行完行被删除 |
| "最近提醒过你"历史 | 每行只有最近一次成功与失败时间，没有逐次记录 |
| 运营统计"126 条进行中" | 要解析每行二进制才能统计 |
| 字段演进 | task_data 是序列化对象，改结构要迁移全部行 |
| 将来换调度框架 | 业务数据锁死在框架私有表里 |

框架自身也要求不要手工读写 scheduled_tasks，把业务查询建在它上面等于耦合到框架内部结构。所以分工是：

- **reminder 表**：提醒是什么、谁设的、什么规则、什么状态。产品数据，生命周期跟用户走。
- **scheduled_tasks**：下一次什么时候执行。运行时状态，生命周期只到下一次执行。
- **reminder_delivery**：每次投递的结果。历史。

判断口径一句话：用户或运营会在页面上看到的，要业务表；只是系统内部到点做一件事的，可以只靠 scheduled_tasks。泡泡 GC 属于后者，提醒属于前者。

### 1.4 为什么同库同事务

scheduled_tasks 与 reminder 表在同一个 PostgreSQL 数据库里。新建提醒时写业务表和排调度行在同一个事务内，回滚时一起回滚，不存在"业务没写成但调度排上了"或者反过来的情况。

这是 db-scheduler 相对 Redis 路线最实质的优势。Redis 路线里"双写不一致靠对账兜底"这一整块问题，在这里根本不存在。

### 1.5 为什么用一次性实例而不是持久化 cron

db-scheduler 支持把 cron 与时区存进任务数据，让框架自动算下一次。本方案对提醒不用它，而是每次投递完由业务重算下一次，再排一个新的一次性实例。原因是"每月几号、按用户时区、遇到夏令时怎么处理"这些规则本来就在业务里，产品页展示下一次时间也要用同一套计算。两处各算一遍，迟早不一致。

### 1.6 为什么它撑得住用户级的量

结论先行：**调度本身不是瓶颈，投递才是；而投递的瓶颈可以用线程数和异步化解决，与调度框架无关。**

**表不会失控。** 每条提醒在任何时刻只有一个"下一次"。一次性任务执行完框架 DELETE 这一行，业务再排下一次；周期任务执行完框架原地 UPDATE execution_time。所以 scheduled_tasks 的行数等于进行中的提醒数加未来 7 天的计划行数，与运行了多久无关。

| 假设 | 行数 |
|---|---|
| 10 万用户，人均 1.3 条进行中提醒 | 13 万 |
| 1 万角色，每日上限 2 条，存 7 天 | 14 万 |
| 合计 | 不到 30 万 |

放大十倍到 300 万行，仍在框架官方基准覆盖的范围内。到点查询走 execution_time 索引的范围扫描加 LIMIT，代价只与"本秒到点的行数"相关，与表总行数无关。真正随时间增长的是 reminder_delivery，那张表需要保留策略，比如只留 90 天。

**数据库压力有数量级余量。** lock-and-fetch 策略下，每批认领是一条 `SELECT ... FOR UPDATE SKIP LOCKED`，完成再一条 UPDATE 或 DELETE。官方在 4 核 PostgreSQL 加 4 台竞争实例的基准上测出每秒约 1 万次执行，数据库事务数约等于执行数。对照日投递 1,204 次，即便全部集中在早晚两个整点，每个整点也不过几百条；三个节点每秒各一次轮询，空转时是三条毫秒级查询。差三到四个数量级。

**真正要设计的是整点洪峰。** 用户提醒天然聚集在整点。假设 10 万用户里 30% 在同一时区设了 08:00 每日提醒，那一秒钟有 3 万条到点。框架认领这 3 万条没有问题，问题在于投递每条要调角色生成话术再推送，假设耗时 2 秒：

| 线程配置 | 并发 | 吞吐 | 3 万条耗时 |
|---|---|---|---|
| 4 线程 × 3 节点 | 12 | 6 条/秒 | 83 分钟，不可接受 |
| 50 线程 × 3 节点 | 150 | 75 条/秒 | 约 7 分钟 |
| Handler 只入队，投递交给异步工作池 | 取决于工作池与下游 | 数百条/秒 | 1 到 2 分钟 |

三条应对措施，按优先级：

1. **线程数按峰值配。** 投递是 IO 等待，线程开到几十个对 CPU 没有压力。这是配置项，不是代码改动。
2. **Handler 做轻。** Handler 只负责认领、回查、写"待投递"记录，然后交给独立的投递工作池或消息队列，立刻返回。框架的线程秒级释放，洪峰被工作池吸收，下游生成与推送的限流也在工作池里做。
3. **提前生成话术。** 到点前几分钟由另一个任务预生成文本，到点时只做推送，单条耗时从 2 秒降到 100 毫秒以内。

这三条都是业务侧的容量设计，换成任何调度框架都同样需要。db-scheduler 的角色是"准时把 3 万条交出来"，这一点有基准数据支撑。以上假设数字（用户数、同时区比例、单条耗时）需要按真实数据替换后再定线程数。

**不会重复、不会丢。**

| 风险 | 机制 |
|---|---|
| 三个节点同时认领同一条 | `FOR UPDATE SKIP LOCKED` 是数据库级互斥，一行只会被一个事务锁到 |
| 同一条提醒被排两次 | 主键 (task_name, task_instance) 唯一，重复 schedule 会被拒绝或按配置改为 reschedule |
| 投递成功但状态没写回，重试后再发一次 | reminder_delivery 以 (业务 id, 计划时刻) 为唯一键，第二次插入失败即跳过推送 |
| 节点在投递中崩溃 | 已认领行带心跳，心跳超时后其他节点重新认领，进入上一行的幂等保护 |
| 数据库不可用 | 调度行是持久化的，恢复后照常认领，不会丢；此时应用本身也不可用，不会产生新的不一致 |
| 停机很久后恢复 | 过期行会被立即认领，Handler 的迟到阈值决定发还是标记错过 |
| 用户在投递的那几秒改期 | reschedule 对已认领行返回 false，业务侧按"下一次生效"处理；Handler 回查时用 version 发现变化则放弃本次 |
| 业务写成功但调度没排上 | 同库同事务，要么都成功要么都回滚 |

**什么时候它不够用。**

- 单节点每秒需要执行的任务数接近千级，且投递无法异步化。应先做上面的第 2 条，再考虑加节点；框架基准显示加数据库核数不再提升吞吐，瓶颈会转到应用侧。
- 需要毫秒级精度。轮询模型的下限是轮询间隔，1 秒已经是合理下限。
- 非 Java 服务要接入。db-scheduler 只有 Java 客户端，其他语言的服务走 xxl-job 的 HTTP 任务。

在可预见的用户规模内，这三种情况都不会出现。

## 2. 目标与边界

- **承担的职责**：粉丝日程提醒、角色朋友圈自动发布、泡泡过期清理这类 coucou-server 内部的到点任务。
- **不承担的职责**：跨服务的系统级 cron 与运营控制台，继续由 xxl-job 负责。
- **原则**：业务表是真相源，db-scheduler 的 scheduled_tasks 只存"什么时候叫哪个 id"。所有改期、取消、重跑走 Java API，不手工改表。

## 3. 接入步骤

### 第一步：引入依赖

- 在 coucou-server 的 pom 里加 db-scheduler 的 Spring Boot starter。它编译目标是 Java 17，与现有 Java 25 加 Boot 3.5.7 兼容，Maven Central 可直接拉取，不需要私有仓库。
- 不引入 Redis、不引入其他调度库。

### 第二步：建表

- 在 `src/main/resources/migrations/` 新增一个编号的 SQL 文件，内容是框架自带的 PostgreSQL 建表脚本，表名定为 `coucou.scheduled_tasks`，DDL 全部加 `IF NOT EXISTS`，符合现有手工迁移流程。
- 顺带在业务表上加两样东西：`reminder` 表加 `version` 列用于改期竞态判断；`moment_plan` 表如果沿用现有 `moment_post.scheduled_publish_at`，只需确认它的 due 索引仍在。

框架自带的表结构（PostgreSQL）：

| 列 | 用途 |
|---|---|
| task_name | 任务类型，如 `reminder` |
| task_instance | 实例 id，与 task_name 组成主键，业务 id 直接放这里 |
| task_data | 任务数据，本方案只放 id 或留空 |
| execution_time | 下一次执行时刻，带时区的时间戳，有索引 |
| picked / picked_by | 是否已被认领、被哪个实例认领 |
| last_success / last_failure / consecutive_failures | 最近成功、最近失败、连续失败次数 |
| last_heartbeat | 执行中实例的心跳，用于崩溃恢复 |
| version | 乐观锁 |
| priority | 优先级，可选 |

### 第三步：配置

沿用现有 `key=${ENV:default}` 风格加到 application.properties。具体配置键以 starter 的 DbSchedulerProperties 为准，建议值：

| 配置项 | 建议值 | 理由 |
|---|---|---|
| 表名 | `coucou.scheduled_tasks` | 与业务表同 schema |
| 轮询间隔 | 1 秒 | 提醒精度到秒，代价是每秒一次索引查询 |
| 轮询策略 | lock-and-fetch | PostgreSQL 走 `FOR UPDATE SKIP LOCKED`，三节点并行认领不重复 |
| 线程数 | 4 起步，按 1.6 节的洪峰估算调整 | 投递是 IO 型，按峰值再调 |
| 心跳间隔 | 保持默认 | 节点崩溃后由其他节点接管 |
| 无法解析任务的删除时长 | 明确设置并知晓 | 避免将来重命名 task_name 后旧行被静默删除 |
| 停机最大等待 | 与 systemd 停止超时对齐 | 让正在投递的提醒跑完 |
| 总开关 | 环境变量控制 | stage 先开、prod 逐节点开 |

### 第四步：注册任务类型

- 新建 `config/SchedulerConfig`，按现有 `<Thing>Config` 命名风格，声明三个 Task 并交给 starter 自动装配的 Scheduler。
- 三个任务类型：

| task_name | 类型 | 实例粒度 |
|---|---|---|
| `reminder` | 一次性 | 每条提醒的下一次触发一个实例 |
| `moment_publish` | 一次性 | 每条计划行一个实例 |
| `bubble_gc` | 周期，每 30 分钟 | 一个实例 |

- 提醒的周期由业务重算，理由见 1.5 节。

### 第五步：业务写入点接调度

在现有 reminder 与 moment 的 Service 层，三个写入点各加一行调度调用，全部放在同一个数据库事务里：

| 业务动作 | 调度动作 |
|---|---|
| 新建提醒 / 生成计划行 | `schedule(id, next_fire_at)` |
| 改期 | 业务表 version 加一，`reschedule(id, newTime)` |
| 取消或暂停 | `cancel(id)` |

### 第六步：Handler 的固定套路

每个 Handler 只做四件事，顺序固定：

1. 回查业务表拿最新数据；不存在或状态不是进行中，直接返回。
2. 判断迟到：当前时间减计划时间超过阈值（提醒建议 30 分钟）则写"错过"记录，不投递。
3. 执行业务动作并写投递日志，投递日志以 (业务 id, 计划时刻) 为唯一键保证幂等。
4. 周期类型重算下一次并 `schedule` 新实例；一次性类型更新业务状态为已结束。

失败处理交给框架的重试策略，建议最多 3 次、指数退避从 1 分钟起。重试耗尽时由失败处理器把业务状态标为失败、触发现有飞书告警，并删除对应的调度行，避免它以"连续失败 N 次"的状态一直留在表里污染运维视图。

### 第七步：运维接口

在现有 admin 域下加三个只读端点，沿用 X-Admin-Token 鉴权：正在执行、连续失败中、按类型汇总。不暴露改期删除接口，那些走业务自己的 reminder 接口。

## 4. 三个场景的落法

| 场景 | 实例来源 | Handler 动作 | 备注 |
|---|---|---|---|
| 粉丝日程提醒 | 用户保存提醒时排一条 | 生成话术、推送、写 reminder_delivery、重算下一次 | 改期取消频繁，全部走 reschedule 与 cancel |
| 朋友圈自动发布 | Studio 侧生成计划行时排一条 | 生成内容并发布，更新计划行状态 | 创作者取消计划行时同步 cancel |
| 泡泡过期清理 | 启动时排一个周期实例 | 删除超过 3 天未处理的行 | 也可以放 xxl-job，二选一，建议放这里以免跨两个引擎 |

## 5. 与 xxl-job 的分工

- xxl-job 里不再建提醒分发器任务，《中央调度中心技术方案》中的 `reminder_dispatcher` 取消。
- xxl-job 保留系统级任务与控制台。
- 运营要看个体任务的健康状况，看第七步的三个端点或接入现有 Micrometer 指标。

---

## 6. 运维注意点

- **热表与膨胀。** 每次认领和完成各一次 UPDATE，PostgreSQL 会产生死元组。行数几十万、每秒几十次更新的规模下默认 autovacuum 足够，上线后观察 `n_dead_tup` 即可，必要时给这张表单独调低 autovacuum 阈值。
- **时钟。** 认领依赖 execution_time 与数据库或节点时间的比较，三个节点必须 NTP 同步。
- **不要改 task_name。** 上线后重命名任务类型会让旧行变成"无法解析"，默认一段时间后被框架删除。
- **没有逐次历史。** 框架只保留每行最近一次成功和失败。投递日志表就是历史，报表从它出。
- **首次导入。** 上线前已有存量提醒的话，用 scheduleBatch 一次性排入。

## 7. 验证与上线

1. **本地**：起服务，建一条 10 秒后的提醒，确认投递；改期到 1 分钟后，确认只投递一次；取消，确认不投递。
2. **多副本**：本地起两个实例指向同一库，建 100 条同一时刻的提醒，确认投递日志恰好 100 条。
3. **崩溃恢复**：投递过程中 kill 一个实例，确认另一个实例在心跳超时后接管。
4. **洪峰**：造 1 万条同一秒到点的提醒，Handler 用 mock 投递，记录从到点到全部完成的耗时，据此定线程数。
5. **stage**：总开关打开，跑通 e2e 现有用例，观察一天。
6. **prod**：三节点按现有 deploy-prod 流程发布，总开关先只在一个节点打开，观察后再全开。CLAUDE.md 要求生产部署先确认，按流程走。

## 8. 工作量

一个迁移文件、一个配置类、三个 Handler、三个写入点各加一行、三个只读端点。核心代码不到 300 行，其余是测试与上线。
